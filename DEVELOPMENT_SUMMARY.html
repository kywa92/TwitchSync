1. Original brief & interpretation

The user's opening request, paraphrased faithfully:

A locally hosted web app that plays two videos side by side in one browser window. Both are pulled from Twitch and stored locally: a large main gameplay video, and a narrow column of chat history in video form to its right. Player controls at the bottom of the page should scrub both videos together, so the chat always matches the moment of gameplay being watched. The purpose is to avoid re-encoding the two together into one file. A chat history in JSON was also supplied, "if that would be a better way of tackling this project."

Two things about this brief shaped everything that followed:

  1. The stated goal was synchronised chat, not literally "play two videos." Playing two videos was the user's proposed mechanism; the actual requirement was "whatever part of the main video I'm watching, I should see the chat for a relevant time on the right." The user explicitly opened the door to the JSON alternative. That made the chat-source question a genuine fork worth asking about rather than assuming — see ADR-01.
  2. The anti-goal was explicit: avoid re-encoding. Any design that required a preprocessing/transcode pass would have defeated the project's purpose, which ruled out several otherwise-attractive options (e.g. pre-rendering chat to frames, remuxing, generating a sprite sheet of chat images).

Two clarifying questions were put to the user before any code was written, each with a recommendation:

QuestionOptions offeredUser's choice
Chat source (a) Render chat from the JSON as real HTML (recommended); (b) play CHAT.mp4 beside the video with a JS sync loop; (c) build both with a toggle (a) Render from JSON
Scope (a) Library picker that auto-pairs any VODs in the folder (recommended); (b) hardcode this single VOD (a) Library picker

The rationale offered for (a) in the first question — and the reason it was recommended — is recorded in ADR-01. The second choice proved important later: because the app was already a multi-VOD library rather than a single hardcoded file, adding NAS support in the final phase was an extension of an existing concept rather than a rewrite.

2. Session timeline

Six phases. Phases 1–3 were the original build; phases 4–6 were follow-up requests from the user, each of which is a self-contained unit of work.

  1. Phase 1 — Investigation and planning (plan mode)

    Direct inspection of media + one Plan subagent · output: approved implementation plan

    Probed the two MP4s with ffprobe, mapped their atom layout, parsed the 90 MB chat JSON structure, and checked what runtimes the machine had. Asked the user the two scoping questions above. Dispatched a Plan subagent with the verified facts to produce a detailed implementation design (see §4). Wrote the final plan to ~/.claude/plans/this-is-a-new-jaunty-lagoon.md and obtained approval before touching the repo.

  2. Phase 2 — Core implementation

    Created server.py + static/ (7 files) · verified with curl and browser automation

    Built the stdlib-only backend first and proved it with curl before writing any frontend — Range semantics being the load-bearing piece, it was cheaper to validate in isolation. Then the single-page frontend: library picker, player with custom control bar, and the chat rendering/sync engine. Three defects were found and fixed during browser verification (§7).

  3. Phase 3 — User documentation

    Created USER_GUIDE.html (752 lines, self-contained)

    A 16-section end-user manual with two custom diagrams (a CSS mock of the player layout and an inline-SVG anatomy of the seek bar), theme-aware, no external resources so it opens straight from Finder.

  4. Phase 4 — Offline-capability audit (user question)

    No code changes · investigation and evidence only

    The user asked whether chat emotes/badges are fetched from the internet at playback time, because they need the app to work with no connectivity. Answered with static analysis plus live runtime evidence (§9). Conclusion: everything is embedded in the JSON; the app makes zero external requests.

  5. Phase 5 — Project logo in the header

    Added /icon.png route + header layout

    Wired the user-supplied icon.png into the library header. Included a small investigation of a console error that turned out to be unrelated (§8).

  6. Phase 6 — Multi-folder / NAS library support

    Rewrote the library layer · new folder-manager UI · 2 further defects fixed

    The largest single change after the initial build. The user asked to point the app at a NAS while keeping the drop-in-project-folder behaviour. Their Synology was already SMB-mounted, so this was implemented as multi-root filesystem scanning rather than any network protocol work. Testing against their real 36-VOD NAS library immediately exposed two latent defects (BUG-04, BUG-05).

3. Investigation: verified ground truth

Every significant design choice in this project traces back to a measured fact rather than an assumption. These were established by direct inspection before or during implementation. Future maintainers should re-verify these if the data source changes (a TwitchDownloader version bump, a different streamer's VOD, a different download configuration).

Critical finding
The moov atom sits at the end of the file (offset 23,876,268,717 of 23,931,038,951). These files are not "faststart". A browser therefore cannot play them at all without HTTP Range support: it must fetch the tail to read the index before decoding a single frame, then request arbitrary interior byte ranges for every seek. Python's http.server has no Range support — verified by source inspection. This single fact made a hand-written Range implementation non-optional (ADR-03).

3.3 Environment

  • Python 3.14.2 present; Node.js absent. This decided the stack outright (ADR-02) — a Node/Vite frontend was not an option without asking the user to install a toolchain, which the brief did not invite.
  • ffmpeg/ffprobe 8.1.2 available — used for investigation only. Deliberately not used at runtime: shelling out to ffprobe per VOD would make the library listing slow and add a hard dependency (ADR-04).
  • macOS (Darwin 25.6.0). Relevant in phase 6: NAS shares appear as ordinary filesystem paths under /Volumes/.

3.4 NAS environment (discovered in phase 6)

  • Share already mounted: //kylan@syn1821._smb._tcp.local/SHARE1821 → /Volumes/SHARE1821 (smbfs). This is why no SMB client code was needed — see ADR-09.
  • /Volumes/SHARE1821/VODs contains 36 valid VOD pairs, plus a nested snowboard day/ subfolder containing more.
  • Extension casing is inconsistent in the real library: 31 files use .Json (capital J) versus 24 using .json. This directly exposed BUG-04.
  • Synology housekeeping directories present: #recycle (contains deleted VODs — must not be listed), @eaDir, #snapshot.
  • The project folder's VOD is a duplicate of one on the NAS (identical byte size), which forced the ID scheme to disambiguate copies (ADR-10).

4. Agent-performed work

Exactly one subagent was invoked in this session. This section is deliberately precise about what it did, because "an agent wrote it" is not a useful provenance record.

AGENT-01 Plan agent — implementation design adopted
Type & mode
subagent_type: Plan, run synchronously (run_in_background: false) because the result gated all subsequent work.
Input brief
A ~1,200-word prompt containing: the confirmed product decisions (JSON chat rendering, library picker) marked do not revisit; every verified fact from §3.1–3.3; the hard constraints (stdlib only, no build step); and an explicit list of known pitfalls to design around (no Range support in stdlib, 90 MB parse in the browser, aborted-request traceback spam, DOM capping, path traversal). Supplying verified facts rather than asking the agent to rediscover them kept its output grounded and avoided duplicate exploration cost.
Output
A complete implementation plan: file layout with per-file responsibilities, the server routing table, the chat rendering pipeline step by step, the sync/seek algorithm, seek-bar interaction model with justification, CSS grid layout, an edge-case matrix, a build order, and a 20-item manual verification checklist.
Independent findings (value added beyond the brief)
The agent re-verified the data itself and corrected three of my stated assumptions, each of which would have produced visible bugs:
  1. Embedded images are not all PNG — they are a PNG/GIF/WebP mix, so MIME must be sniffed per asset (animated emotes would otherwise have failed to render).
  2. Declared width/height are the logical CSS size while the stored bitmap is × imageScale — rendering at natural size would have made every emote double-size.
  3. Badge image data lives under versions[ver].bytes, not a data field.
It also quantified that 1,820 comments lack user_color, upgrading the colour-hash fallback from "nice to have" to mandatory.
How much was adopted
Substantially all of it. The implemented file layout, routing table, chat pipeline, sync engine, seek model, and CSS grid match the plan. Its verification checklist was executed against the running app.
Where implementation diverged
  • The agent proposed a --dir-only single library root; phase 6 replaced this with multi-root scanning (not a correction — a later requirement it was never given).
  • Its ThreadingHTTPServer traceback-hygiene advice covered the stream loop and finish(); in practice a third site was needed (handle()) — see BUG-02.
  • Chapter tick marks on the seek bar were listed as an optional stretch item and were not built.
  • It suggested a single app.js as an alternative but justified ES modules; modules were used.

Agents deliberately not used

No Explore agents were dispatched. The plan-mode workflow offers them for codebase reconnaissance, but this repository was empty — there was no existing code to search. Direct ffprobe/Read/Python inspection of the media files was both cheaper and more precise than delegating. Likewise no agents were used in phases 2–6: that work was iterative build-and-verify against a running server, where delegation would have added context-transfer overhead without parallelism benefit.

5.1 Backend responsibilities (server.py)

  • Library class — owns the set of library roots (one permanent + N user-added, persisted to folders.json), recursive pairing scan, head-metadata caching, and ID→path resolution. All mutating and scanning operations are guarded by a single threading.Lock.
  • Handler — routing, Range/206 streaming, static serving, JSON API, POST body validation, and log hygiene.
  • Module-level log worker — a daemon thread draining a bounded queue (ADR-14).
  • ThreadingHTTPServer bound to 127.0.0.1, HTTP/1.1 keep-alive (safe: every response sets Content-Length).

The engine holds two invariants worth preserving in any future edit: (1) cursor is always the index of the next comment not yet appended, and (2) the DOM contains a contiguous suffix of comments ending at cursor - 1. Every operation (tick, seek-rebuild, trim) preserves both.

6. Design decisions

Sixteen decisions with material consequences. Format: context → decision → rationale → consequences.

ADR-01Render chat from JSON rather than playing the chat videouser-approved
Context
The brief proposed playing CHAT.mp4 beside the gameplay video, kept aligned by a JavaScript sync loop. A chat JSON was also available.
Decision
Render chat as live HTML from the JSON, driven by the video's clock. The chat videos are ignored entirely.
Rationale
Browsers cannot hard-lock two <video> elements. Any two-video approach needs a correction loop that periodically re-seeks the laggard, which produces visible hitches; after a scrub both elements re-buffer independently; and the 700×2400 chat video would be downscaled into a ~380 px column, softening text. Rendering from JSON makes sync exact by construction — there is no second clock to drift — and yields sharp, selectable text, lower CPU, instant seek response, and a free chat-activity histogram. It also makes the 3.57 GB chat renders deletable.
Consequences
Required implementing Twitch's rendering semantics by hand (emote matching, zero-width overlays, badge lookup, colour fallback). Adds a one-time per-VOD cost: fetching and parsing a large JSON. Accepted deliberately; see §13 for the caching option not taken.
ADR-02Python stdlib backend, zero-build vanilla frontend
Context
Node.js is not installed on the machine; Python 3.14.2 is.
Decision
Backend uses only the Python standard library. Frontend is hand-written HTML/CSS plus native ES modules — no bundler, no transpiler, no package manager.
Rationale
The app must start with one command on a machine the user already has. Introducing a toolchain would add an install step, a lockfile, a build step before every run, and a supply chain — all for a single-user local player. ES modules are served over HTTP here, so they work natively without a bundler.
Consequences
Things a framework would provide (reactive rendering, routing) are written by hand — roughly 1,200 lines of frontend. In exchange there is nothing to update, nothing to audit, and the app will still run unchanged years from now.
ADR-03Hand-implement HTTP Range semanticsload-bearing
Context
moov at EOF (§3.1) + no Range support in http.server.
Decision
Full single-range support: bytes=start-end, start-, and -suffix forms; 206 with Content-Range; 416 + Content-Range: bytes */size for unsatisfiable; malformed headers fall back to 200 full-body per RFC; 1 MiB streaming chunks. Multi-range requests are served as their first part only.
Rationale
Without this, playback does not work at all — not "is slow," but cannot start. Suffix ranges specifically matter because the browser's very first request after Content-Length discovery is for the file tail to locate moov. Multi-range was skipped because no browser issues it for media playback; serving the first part is a legal, safe degradation.
Consequences
~45 lines of well-tested code. Enables instant seeking across a 43.7 GB file and means the client only ever transfers what it watches.
ADR-04Head-parse 64 KB for library metadata instead of reading the whole JSON or calling ffprobe
Context
The library card shows real stream title, streamer, game, and duration. Those live in the chat JSON (90 MB each) or could come from ffprobe.
Decision
Read the first 64 KB of each chat JSON, locate the "streamer" and "video" keys, and parse just those objects with json.JSONDecoder().raw_decode(), which parses one value and ignores the truncated remainder. Cache per (path, size, mtime). On any failure, fall back to the filename.
Rationale
The metadata reliably appears within the first ~750 bytes, so 64 KB has ~85× headroom (enough for many chapters). Loading 90 MB × N files per library visit would make the picker unusable, especially over SMB; shelling out to ffprobe would add a hard external dependency and process-spawn latency per VOD. This approach costs one small read per file, once, then nothing.
Consequences
Measured at 0.03 s per file over SMB. If TwitchDownloader ever moves comments before video in its output, this degrades gracefully to filename titles rather than breaking.
ADR-05Seek bar commits on pointer release, not during the drag
Context
Dragging a scrubber conventionally seeks live for instant feedback.
Decision
During a drag, only the visuals move (fill, handle, tooltip, time readout). video.currentTime is assigned once, on pointerup. Keyboard seeks commit immediately.
Rationale
Each currentTime assignment on these files aborts in-flight range requests, opens new ones, and forces a backward keyframe hunt. Live-seeking a drag would fire dozens of those cycles per gesture — stuttering video, socket churn, and repeated chat rebuilds. Thumbnail previews (the usual reason to seek live) aren't available without a preprocessing pass, which the anti-goal forbids, so the time tooltip conveys everything a live seek would.
Consequences
Scrubbing feels instant. Six rapid seeks in a row produced zero server errors and no stalls.
ADR-06Chat DOM is a bounded window, not the full log
Context
20,514 messages per VOD; a 12-hour VOD has more.
Decision
Keep at most 200 message elements while pinned to the bottom; raise the cap to 500 while the user is reading scrollback; trim from the top. Seeks rebuild the window from a binary search with 50 messages of backfill.
Rationale
Rendering all messages would create tens of thousands of nodes and thousands of images — slow and memory-hungry for content that is off-screen anyway. The raised cap during scrollback exists because trimming from the top while the user reads would shift content under them; the trim is deferred until they re-pin, and when trimming does occur while unpinned, scrollTop is compensated by the removed height so the view never jumps.
Consequences
Constant-cost chat regardless of VOD length. Old messages are not scrollable-to indefinitely — seek backward instead, which is the natural gesture anyway.
ADR-07Decode embedded images once into Blob URLs
Context
1,077 images arrive base64-encoded inside the JSON. The same emote appears in hundreds of messages.
Decision
At load, decode each asset once (atob → Uint8Array → sniff magic bytes → Blob → createObjectURL), store the URL in a lookup map, and record every URL for revocation on teardown.
Rationale
Data URIs would re-decode the same base64 on every message render and bloat the DOM with megabyte-long attribute values. Blob URLs are cheap handles the browser can cache and animate natively — GIF and WebP emotes animate for free with no extra code. MIME sniffing (rather than assuming image/png) is required because the assets are a PNG/GIF/WebP mix.
Consequences
~950 decodes ≈ 53 MB, once per VOD open, under the loading overlay. Teardown must revoke them all or repeated open/close leaks memory — this is why Chat.destroy() exists and is called from main.js.
ADR-08Media paths resolve through an opaque key, never string-to-path math
Context
The client asks for media by a ?v= parameter. The naive design joins that onto a base directory.
Decision
The v value is only ever a dictionary key into the results of a directory scan. It is never joined, normalised, or otherwise treated as a path. A realpath containment check against the known roots is applied as a second, independent layer.
Rationale
Traversal bugs come from path arithmetic on untrusted input. If the value is a lookup key, ../../../etc/passwd is simply a key that does not exist — there is no string to sanitise and no encoding trick to defeat. The containment check is defence in depth for the case where a scan somehow yields a symlinked path outside a root.
Consequences
Verified: traversal attempts return 404, and only files discovered as valid VOD pairs are ever served.
ADR-09NAS support via mounted filesystem paths, not an SMB client
Context
The user asked to point the app at a NAS over 2.5 GbE.
Decision
Treat a NAS as an ordinary directory path (e.g. /Volumes/SHARE1821/VODs). The user mounts the share in Finder; the app just reads it. Mounted volumes are offered as clickable suggestions in the UI.
Rationale
Speaking SMB directly would require a third-party library (violating ADR-02) and would mean the app handling NAS credentials — something it should never do. Finder already solves mounting properly, stores credentials in Keychain, and can auto-mount at login. Piggybacking on the OS mount is strictly better: less code, no secrets, and it works identically for external drives, SD cards, and any future storage.
Consequences
The user must mount before use; an unmounted share shows as not mounted and is skipped rather than erroring. The /Volumes suggestion list is macOS-specific — see §13.
ADR-10Composite VOD IDs, with a stem fallback for old links
Context
Before phase 6 a VOD's ID was its filename stem. With multiple folders, the same stem can exist in several places — the user's project folder holds a byte-identical copy of a NAS VOD. Subfolders can also repeat stems within one root.
Decision
ID is <rootId>:<relative path without extension>, where rootId is the first 8 hex of SHA-1 of the root's realpath. Resolution tries an exact ID match first, then falls back to matching any VOD whose bare stem equals the value.
Rationale
The composite disambiguates duplicates deterministically and survives restarts (unlike an array index). The fallback preserves URLs bookmarked before the change — an old ?v=<stem> link still resolves instead of 404ing, which matters because the user had been using the app for a day already.
Consequences
Renaming a folder changes its rootId and therefore its VOD IDs; bookmarks then fall back to stem matching, which still works. See ADR-15 for why saved playback positions were deliberately not keyed on this ID.
ADR-11Case-insensitive extension pairing
Context
The real NAS library contains 31 .Json files and 24 .json files.
Decision
Within each directory, build a lowercase-name → actual-name map and look up (stem + ".json").lower(). The .mp4 test and the " - CHAT" exclusion are likewise case-insensitive.
Rationale
TwitchDownloader has emitted more than one casing across versions. Python's dict lookup is case-sensitive even when the underlying filesystem is not, so the original exact-match pairing silently dropped over half the user's real library — a failure mode that produces no error, just missing entries.
Consequences
Fixed BUG-04. Also future-proofs against .JSON.
ADR-12Recursive scan, depth-limited, with a skip list
Context
The user's NAS keeps VODs both at the top level and in per-event subfolders. A share root also contains large unrelated trees and NAS system directories.
Decision
Walk each root up to 4 levels deep, pruning hidden directories (leading .) and a skip list: @eaDir, #recycle, #snapshot, node_modules, __pycache__.
Rationale
Non-recursive scanning would have missed real VODs; unbounded recursion over a multi-terabyte share would make every library visit slow. Four levels covers realistic organisation while bounding worst-case cost. #recycle is excluded specifically because it is the NAS trash — surfacing deleted VODs as playable would be actively misleading, and the user's recycle bin does contain old VODs.
Consequences
Measured 0.04 s to walk the user's NAS VOD tree. VODs nested deeper than 4 levels require adding their folder directly — documented in the guide's troubleshooting section.
ADR-13CSRF protection by requiring a JSON content type
Context
Phase 6 introduced the first state-changing endpoint (POST /api/folders). Any website the user visits can issue cross-origin requests to 127.0.0.1.
Decision
Require Content-Type: application/json; reject anything else with 415. Never answer OPTIONS. Keep all read endpoints on GET with no side effects.
Rationale
A cross-origin fetch carrying a JSON content type is not a CORS "simple request", so the browser must preflight it with OPTIONS. Since the server never answers that preflight, the real request is never sent. Form-encoded posts (which are simple and would otherwise sail through) are rejected outright. This gets meaningful protection from a content-type check rather than token plumbing that would be overkill for a single-user local app.
Consequences
Verified: a form-content-type POST returns 415. A malicious page cannot add or remove library folders.
ADR-14Logging happens on a background thread with a bounded queue
Context
Discovered the hard way — see BUG-05. BaseHTTPRequestHandler.send_response() calls log_request() before writing the response, so a blocking log write blocks the response.
Decision
Handlers enqueue formatted log lines with put_nowait onto a 2,000-slot queue; a daemon thread drains it to stderr. If the queue is full, the line is dropped.
Rationale
If stderr is a pipe nobody drains, write() blocks once the pipe buffer fills. On a threaded server every logged request then hangs — and because handlers hold the library lock, unrelated requests hang too. The app appears frozen with no error anywhere. Dropping log lines is obviously preferable to freezing the application; logs are diagnostic, serving video is the product.
Consequences
Request threads can no longer block on output. Log lines may be dropped under extreme pressure (never observed in practice). Startup banner prints use flush=True so they appear immediately even when redirected to a file.
ADR-15Saved playback position is keyed by filename stem, not by VOD ID
Context
Resume positions live in localStorage. Phase 6 changed VOD IDs (ADR-10).
Decision
Keep the key as ts.pos.<stem> — deliberately not updated to the new composite ID.
Rationale
Two benefits fall out of this. Existing saved positions survived the ID change with no migration. And because the user keeps a local copy of a NAS VOD, opening either copy resumes from the same place — the position follows the content rather than the storage location, which is what a viewer actually means by "where I was."
Consequences
Two genuinely different VODs that share a filename stem would share a resume position. Acceptable: identical stems almost always mean identical content, since the stem encodes date and stream title.
ADR-16Serve the logo from the app directory, not the media root
Context
icon.png sits in the project root, which is also a library folder — but --dir can point the library elsewhere entirely.
Decision
A dedicated /icon.png route resolves against APP_DIR (where server.py lives), independent of any library folder. No duplicate copy is placed in static/.
Rationale
The logo is an application asset, not media. Resolving it against the library root would break the header the moment someone runs --dir /Volumes/NAS/VODs. Keeping the single copy in the project root also lets it double as the repository logo.
Consequences
The <img> uses alt="" because the word "TwitchSync" sits beside it — correct treatment for a decorative image, and it means a missing file degrades to nothing rather than stray alt text.

7. Defects found & fixed

All five were found by verification against the running application or real data — none by code review alone. That is the argument for the build-then-verify-live loop used throughout.

BUG-01Play/pause, mute and fullscreen icons never toggledfunctional
Symptom
Video played correctly but the control bar always showed the "play" triangle, never the pause bars. Same for the mute and fullscreen icon pairs.
Root cause
The icons are inline <svg> elements and the code set element.hidden = true/false. SVGElement has no hidden IDL property — verified at runtime: "hidden" in SVGElement.prototype === false. The assignment created a meaningless expando property; the CSS [hidden] rule matches the attribute, which was never written. It fails silently with no error.
Fix
A show(node, visible) helper in player.js that toggles the attribute via setAttribute/removeAttribute. Applied to all three icon pairs.
Lesson
The hidden property is an HTMLElement convenience, not a universal DOM feature. For SVG (and MathML) always toggle the attribute.
BUG-02Traceback spam from reset keep-alive connectionsnoise
Symptom
Multi-line ConnectionResetError tracebacks in the server terminal during normal use.
Root cause
Guards existed on the streaming loop and on finish(), but the reset surfaced from a third place: handle_one_request() blocking on rfile.readline() while a keep-alive connection waits for its next request. When the browser discards a media connection mid-scrub — which it does constantly — that read raises, and socketserver prints the traceback.
Fix
Override handle() to swallow BrokenPipeError/ConnectionResetError, joining the existing guards at the other two sites.
Lesson
With HTTP/1.1 keep-alive there are three distinct places a client disconnect can surface: mid-write, at flush during finish(), and at the idle read between requests. All three need handling.
BUG-03Space-bar shortcut ignored when key events carry an empty keyrobustness
Symptom
Space did not toggle playback under automated key injection; m and other letters worked.
Root cause
Instrumenting keydown showed genuine trusted events arriving with key: "", code: "", keyCode: 0 for space. The handler switched on e.key, so the case never matched.
Fix
Resolve the key as e.code === "Space" ? " " : e.key before the switch.
Honest scope note
This originates from the automation layer, not from real keyboards — a human pressing space produces key: " ". The fix is defensive hardening rather than a user-facing bug fix, and is recorded as such rather than overclaimed.
BUG-04Case-sensitive pairing silently hid over half the NAS librarydata loss (visibility)
Symptom
Would have manifested as VODs simply not appearing in the library, with no error or warning.
Root cause
Pairing looked up stem + ".json" in a Python dict built from scandir names. Dict lookups are case-sensitive even though macOS/SMB filesystems are typically not. The user's real library contains 31 .Json files versus 24 .json, so 31 VODs would have been invisible.
Fix
Case-insensitive extension matching (ADR-11).
Lesson
This class of bug is invisible to synthetic test data — it only appeared because the implementation was pointed at the user's actual archive, accumulated across years and tool versions. Test against real data.
BUG-05A stalled output pipe froze the entire serveravailability
Symptom
A POST /api/folders hung for over 120 seconds with no response. The configuration file had been written, so the work had completed — yet nothing came back. Subsequent GET /api/videos also hung.
Diagnosis
The decisive observation: GET / returned in 35 ms while every /api/* path hung. The only behavioural difference between them is that log_request logs API paths and skips static ones. That isolated the fault to the log write. Confirmed by running the same server with stderr redirected to a file, where the identical POST returned in milliseconds.
Root cause
The harness capturing the server's output stopped draining its pipe. Once the pipe buffer filled, sys.stderr.write() blocked. Because send_response() logs before writing the response, the handler thread blocked while still holding the library lock, so every other library request queued behind it. The app looked frozen with no error anywhere.
Fix
Background log worker with a bounded, drop-on-full queue (ADR-14).
Lesson
Worth internalising generally: writing to stdout/stderr is a blocking I/O operation on a resource you do not control. Any server that logs synchronously on the request path can be frozen by whatever is (not) reading its output — a piped launcher, a paused terminal, a log collector that stalls.

11. Security model

  • Network exposure: the server binds 127.0.0.1 only. Nothing is reachable from the LAN or internet; verified during setup.
  • Path handling: opaque-key resolution plus realpath containment (ADR-08). Only files discovered as valid VOD pairs inside a configured root can be served.
  • State-changing endpoints: one (POST /api/folders), protected by the JSON content-type requirement (ADR-13). Adding a folder is the only way to widen what the server can read, and it requires a deliberate local action.
  • Credentials: the app never sees, requests, or stores any. NAS authentication is delegated entirely to macOS/Finder/Keychain (ADR-09).
  • Outbound traffic: none. The application makes zero external requests — proven by network-log inspection, not just by reading the code (§9.3).
  • Data integrity: the server only ever opens media files for reading. The only file the app writes is folders.json in the app directory.
  • Untrusted input rendered: chat messages are user-authored text from Twitch. They are inserted with textContent and createTextNode — never innerHTML — so message content cannot inject markup or script.

13. Known limitations & future work

13.1 Accepted limitations

LimitationDetail and reasoning
Chat re-parsed on every openThe 90 MB JSON is fetched, parsed and decoded each time a VOD opens (~2–4 s under a progress overlay). A preprocessed sidecar cache — compact binary index plus a sprite/asset bundle — would make this near-instant. Deliberately not built: it adds a preprocessing step, which is precisely what the project set out to avoid, and the cost is paid once per viewing session.
No seek-bar thumbnailsWould require decoding frames ahead of time (a preprocessing pass). The chat-activity histogram was built instead and arguably serves the "find the good part" need better for this content.
Bits/cheermotes render as plain textExactly one comment in the sample VOD spends bits. Full cheermote tier rendering was judged not worth the complexity; the message still reads correctly.
Profile avatars not shownTheir URLs exist in the JSON but are never requested — rendering them would break the offline guarantee. Twitch chat does not show avatars either.
Multi-range requestsOnly the first range of a multi-range request is served. Legal, and no browser issues them for media.
Scan depth capped at 4Deeper VODs need their folder added directly. Documented in the guide.
No authenticationBy design: localhost-only, single user.

13.2 Untested or environment-limited

  • Fullscreen has not been exercised in a real browser — the embedded preview pane blocks the API (§8). The implementation is the conventional requestFullscreen() on the whole player grid, but a maintainer should confirm it, including the 3-second control auto-hide behaviour.
  • Platform portability. The server itself is portable Python, but the mounted-volume suggestion chips enumerate /Volumes, which is macOS-specific. On Windows or Linux the chips would simply be empty — folders can still be added by typing a path. Extending list_volumes() with /media, /mnt and drive letters would be a small, self-contained improvement.
  • Stale network mounts. Availability is a plain os.path.isdir() check. A hung (rather than absent) SMB mount could block a scan, since there is no timeout around filesystem calls. Not observed; would need a watchdog thread to handle properly.

13.3 Suggested next steps, roughly by value

  1. Verify fullscreen and control auto-hide in a normal browser tab.
  2. Optional chat sidecar cache (§13.1) if the open-time delay becomes annoying in daily use.
  3. Chapter markers on the seek bar — the data is already parsed and returned in /api/videos, it is only unused by the UI. This was the Plan agent's stretch suggestion.
  4. Cross-platform list_volumes().
  5. Housekeeping: __pycache__/ currently shows as untracked in git status and could be added to .gitignore (left alone here because the user has since edited that file themselves).

Appendix B — chat JSON format notes

Reference for anyone extending the renderer. Structure as emitted by TwitchDownloader with image embedding enabled.

{
  "FileInfo":  { "Version", "CreatedAt", "UpdatedAt" },
  "streamer":  { "name", "login", "id" },
  "clipper":   null,
  "video":     { "title", "id", "created_at", "start", "end", "length",
                 "viewCount", "game", "chapters": [ { "startMilliseconds",
                 "lengthMilliseconds", "description", "gameDisplayName", … } ] },
  "comments":  [ {
      "_id", "created_at", "channel_id",
      "content_offset_seconds",              // seconds from stream start — the sync key
      "commenter": { "display_name", "name", "logo", … },
      "message": {
        "body",                              // plain text, fallback if fragments absent
        "bits_spent",
        "fragments":   [ { "text", "emoticon": null | { "emoticon_id" } } ],
        "user_badges": [ { "_id", "version" } ],
        "user_color":  "#RRGGBB" | absent,   // absent for 1,820 of 20,514 here
        "emoticons":   [ { "_id", "begin", "end" } ]   // legacy index form; unused
      } } ],
  "embeddedData": {
    "firstParty":   [ { "id", "imageScale", "data", "name", "width", "height" } ],
    "thirdParty":   [ { "id", "imageScale", "data", "name", "width", "height",
                        "isZeroWidth" } ],
    "twitchBadges": [ { "name", "versions": { "<ver>": { "bytes", "title",
                                                       "description" } } } ],
    "twitchBits":   [ { "prefix", "tierList" } ]
  } }

Rendering rules implemented

  1. First-party emotes — a fragment with a non-null emoticon is looked up by emoticon_id in firstParty. On a miss, the fragment's text is rendered instead (graceful degradation, never a broken image).
  2. Third-party emotes (BTTV/FFZ/7TV) — text fragments are split on spaces and each word is looked up by name in thirdParty. This is why they need whole-word matching rather than substring scanning.
  3. Zero-width emotes — an isZeroWidth hit immediately following an emote (with only whitespace between) is appended inside the previous emote's wrapper span, absolutely centred, so multiple effects stack on one base emote. If there is no eligible base, it renders as an ordinary emote.
  4. Badges — looked up as ` ${_id}/${version} `; unknown badges are skipped silently rather than leaving a gap.
  5. Sizing — images are given the declared width/height, because the stored bitmap is imageScale× larger.
  6. Colours — user_color when present; otherwise Twitch's own default algorithm, (firstCharCode + lastCharCode) % 15 indexed into the standard 15-colour palette, so colourless users are stable across sessions and match what Twitch would show. Any colour too dark to read on the dark panel is blended toward white proportionally to its darkness.
  7. Text nodes — consecutive plain words are coalesced into a single text node rather than one per word, which materially reduces node count over thousands of messages.
